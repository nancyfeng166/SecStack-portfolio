# SecStack

[![Python 3.10](https://img.shields.io/badge/python-3.10-blue.svg)](https://www.python.org/)
[![FastAPI](https://img.shields.io/badge/FastAPI-0.115-009688.svg)](https://fastapi.tiangolo.com/)

[![MCP](https://img.shields.io/badge/MCP-STDIO%20%7C%20SSE-7CB342.svg)](https://modelcontextprotocol.io/)

SecStack 是一个以资产图谱为中枢的安全方法论编排平台——每个安全域不是零散的工具脚本，而是一套完整的、可独立落地的最佳实践方案，通过统一的资产图谱实现跨域联动。与安全工具堆叠的本质区别在于：传统方案每样做一件事且发现互不关联，SecStack 将所有发现挂载到同一资产节点上，让漏洞、攻击面、数据分级、合规状态在同一张图上形成关联。核心价值是让安全从"事后发现孤立的漏洞列表"变成"事前推演有上下文的攻击叙事，事中自动化阻断，事后可审计闭环"。

## 一句话架构

SecStack = 资产图谱（自研图引擎 + SQLite 闭包表）+ 7 套独立安全方法论 + LangGraph 约束编排

三个设计锚点：

1. **所有安全发现统一挂载到资产节点**——漏洞、攻击面、数据分级、基线状态在同一张图上关联，打破工具孤岛
2. **每个安全域是完整方法论而非工具脚本**——SCA 从 BOM 到豁免有 7 个环节，基线从"应使用安全配置"翻译为"禁止 XXX / 必须启用 XXX"
3. **LLM 被约束在状态机里**——不是自由对话，是六节点图调度 + 人工审批断点 + 四层防线

> 阅读指南：本文档是 SecStack 的完整技术白皮书。AppSec 背景建议从 SCA 和攻击面推演开始；红队背景建议从 AI 渗透开始；架构决策见「关键架构决策」章节。

## 项目定位

SecStack 是一个以资产图谱为骨架、LLM 为调度引擎的企业全栈安全智能平台——将 30+ 安全能力模块挂载到统一的资产图谱上，由 AI 大脑编排从发现到修复到验证的完整闭环。它解决的四条根本矛盾，对应下文「核心安全方案」各章节：

1. **工具割裂 → 统一上下文**：传统安全工具各自为政——漏洞扫描不管资产归属、渗透测试不管合规要求。SecStack 用资产图谱 + 闭包表把所有发现锚定到同一资产节点（→ 2.1 资产图谱、2.4 攻击面推演）。
2. **AI 能力 vs AI 风险**：LLM 既是安全引擎也是攻击面——既能推演攻击链，也可能被注入、越权、投毒。解法是"用 AI 做安全，同时给 AI 做安全"：四层沙箱防线 + 五层注入检测 + 哈希链审计（→ 2.8/2.9/2.10/2.13）。
3. **事后发现 → 事前阻断**：安全能力散落在 SDL 各阶段，靠人工衔接。SecStack 把检查嵌入研发每一环节——pre-commit 密钥阻断 → CI 门禁 → 发布裁决（→ 2.6 SDLC 安全门禁）。
4. **生产敏感 → 推演验证**：云资产不敢直接主动扫描。SecStack 以"推演"替代——已知漏洞 + 资产拓扑输入 LLM 推理攻击路径，关键节点受控验证、人工裁决（→ 2.4/2.8/2.12）。

## 2. 核心安全方案

### 2.1 资产图谱引擎

**一句话定义**：资产台账作为全平台坐标系——向所有安全能力供血、定靶，所有安全能力的发现反哺回台账。将逻辑资产（产品/服务/API）和物理资产（主机/数据库/容器/仓库）统一建模，通过闭包表存储拓扑关系，让每个安全发现都有资产上下文。

**解决的安全本质问题**：安全工具缺乏统一的资产上下文——漏洞扫出来不知道影响哪个业务，数据分类不知道关联哪个数据库实例，攻击路径不知道从哪个入口到哪个核心资产。本质是安全管理与资产管理在数据层面断裂。

**方法论简述**：资产注册 → 类型约束校验（40+ 类型 × 父子合法关系矩阵）→ 闭包表路径构建（ancestor, descendant, depth）→ 指纹引擎自动推导 ATT&CK 技战术 → 影子资产发现（扫描发现无主资产时自动创建 unconfirmed 节点）→ 安全状态聚合（漏洞计数/攻击面标签/数据分级）→ 风险沿祖先链冒泡 → 变更触发路径缓存失效。

**关键设计决策**：

- **逻辑/物理双模而非单一资产类型**：安全分析需要两种视角——业务视角（"用户中心服务"有没有安全风险）和基础设施视角（"10.0.1.5 这台主机"暴露了什么端口）。双模设计让同一个安全发现既能按业务归属追溯（影响哪个产品），又能按物理拓扑推演（攻击者从哪台机器打到哪台机器）。代价是建模复杂度增加——需要维护逻辑-物理之间的关联边（deploy_on / uses_db / exposes_api / source_from）。

- **影子资产兜底而非丢弃无主发现**：安全扫描经常发现"不在资产台账里的东西"——一台没登记的主机、一个没纳管的 API 端点、一个文档之外的数据库。传统做法是丢弃或标记为"未知资产"，信息就此丢失。SecStack 的做法：OrphanCorrelator 先尝试正则提取指纹（IP/域名/仓库 URL/DB 连接字符串）→ 指纹匹配失败则走 LLM 语义提取 → 仍然匹配不到则自动创建 status=unconfirmed 的影子资产节点。后续人工审核时可将影子资产"转正"——status 变为 confirmed 后，该节点上的所有历史发现自动激活，参与攻击图构建和风险冒泡。代价是资产池会混入噪音（假阳性影子），通过定期清理长期未转正的影子节点（> 90 天无活动）来控制。

- **闭包表而非递归 CTE 做子树查询**：安全运营最频繁的查询是"某个产品线下所有主机的漏洞汇总"和"从数据库到公网出口经过哪些节点"。闭包表将 O(n) 递归变为 O(1) EXISTS 查询。代价是写入时多维护一张路径表——资产树每次变更都要重建受影响的路径行。但资产变更频率远低于查询频率，这个权衡成立。

- **等级跳变熔断**：当自动分级算法将资产安全等级跨 2 级以上跳变时，系统标记 `pending_review` 并生成审计 finding，而非静默接受。这层熔断机制防止 AI/规则误标导致资产保护策略大幅偏离。

**能力闭环**（台账自我进化飞轮——"供血 → 反哺 → 更准"）：

- **发现**：SCA/SAST/DAST/渗透/数据安全扫描发现无主资产 → 自动创建 `[Shadow]` 影子节点（`source='auto_extracted'`、`status='unconfirmed'`），挂 unclassified-zone 虚拟根，不污染业务树；
- **归因**：无主 Finding 由 `OrphanCorrelator` 正则 + LLM 提取指纹，自动归因到最近资产；
- **治理**：安全运营对影子资产转正（`source='manual'`、`status='confirmed'`，参与正式拓扑与风险评分）或驳回；
- **反哺**：渗透结束 `pentest_asset_writeback` 把端口/技术栈/CPE/漏洞幂等回写；SCA/SAST 把 CVE/代码漏洞挂回 asset_id；
- **呈现**：风险冒泡到祖先节点 → `RiskScorer` 综合评分 → `heatmap-products`/`heatmap-assets` 只读呈现热力图，任意节点可查完整安全画像（漏洞 + 攻击面 + 数据等级 + 合规状态）。

![资产台账自进化飞轮](images/资产台账.png)

> **资产台账自进化飞轮**：发现（扫描反哺无主资产，自动创建影子节点）→ 归因（正则 + LLM 指纹匹配）→ 治理（转正/驳回）→ 反哺（渗透/SCA/SAST 幂等回写）→ 呈现（风险冒泡 → 热力图）——台账为安全能力定靶，安全能力反哺台账，形成自我进化闭环。

![资产热力图](images/资产热力图.png)

> **资产风险热力图**：实时展示核心资产的风险状态（注：通过四象限虚拟位置展示资产的网络位置，通过台账资产通过血缘解析呈现真实的资产交互关系，可以下沉到微服务级别）

### 2.2 漏洞生命周期管理

**一句话定义**：将漏洞从发现到修复的全过程建模为有限状态机，每个状态流转记录审计日志。

**解决的安全本质问题**：漏洞管理的痛点不是"扫不出来"，而是"扫出来之后无人跟进、无法追溯、无法衡量修复效率"。没有状态流转的漏洞列表随时间增长变成噪音——团队学会忽略它。

**方法论简述**：扫描发现 → open（待修复）→ in_progress（修复中）→ fixed（已修复）→ closed（已关闭）。两条旁路：false_positive（误报）和 accepted_risk（已接受风险），均可回退到 open。每次状态变更写入 audit.jsonl（操作人、时间戳、旧状态、新状态、备注），支持按严重级别、状态、时间范围聚合统计。

```mermaid
stateDiagram-v2
    [*] --> open : 扫描发现
    open --> in_progress : 开始修复
    open --> false_positive : 确认为误报
    open --> accepted_risk : 接受风险
    in_progress --> fixed : 修复完成
    in_progress --> false_positive : 确认为误报
    in_progress --> accepted_risk : 接受风险
    fixed --> closed : 验证通过
    fixed --> in_progress : 验证不通过，重新修复
    closed --> in_progress : 漏洞复现，重新打开
    false_positive --> open : 重新评估
    accepted_risk --> in_progress : 条件变化，启动修复
    accepted_risk --> open : 重新评估
```

**关键设计决策**：

- **VALID_TRANSITIONS 硬约束而非自由流转**：漏洞状态不是任意流转的——只能沿预定义的合法路径迁移（如 fixed 只能到 closed 或回退到 in_progress，不能直接到 open）。这层约束防止误操作（如把 CRITICAL 漏洞从 fixed 直接标为 closed 跳过验证），同时让自动化流程能依赖确定的状态语义。代价是灵活性降低——某些组织的修复流程差异需要改代码适配。

**闭环**：各模块扫描 → VulnStore.create() 创建 open 记录 → 修复后 update_status(fixed) → 验证后 update_status(closed) → audit.jsonl 完整审计链。

### 2.3 软件供应链安全治理

**一句话定义**：从 SBOM 生成到漏洞匹配到修复选型到豁免审批的完整方法论，不是 CVE 扫描器。

**解决的安全本质问题**：供应链安全的痛点不是"能不能扫出 CVE"，而是扫描结果和修复路径脱节——扫出来一堆 CVE，开发者不知道先修哪个、修到什么版本最安全又不破坏兼容性、修完怎么验证、修不好的怎么兜底。本质是缺少从发现到治理的连贯决策链。

**方法论简述**：BOM 解析（Docker 内执行 cyclonedx-maven-plugin，非 pom.xml 字符串匹配）→ 依赖路径构建（过滤 Maven 调解淘汰的幽灵边，introduced_by 多对多归因）→ 双源 CVE 匹配（OSV.dev REST API + 11 个离线 CVE JSON，自动降级）→ 杠杆排序（leverage = Σ 子树去重漏洞加权 + λ×max(子树许可证传染分)，先修一个父依赖消除 N 个子传递漏洞）→ 三圈版本选型（安全圈 ∩ 兼容圈 ∩ 稳定圈，拒绝预发布和 <7 天新发布防投毒）→ 四段哈希链锚定（git_commit→pom_hash→bom_hash→vuln_set_hash）→ verify-rescan 比对 delta（eliminated/new/unchanged）→ 双签豁免兜底（dev_lead + sec_lead，90 天到期自动阻断）。

![SCA 供应链深度治理闭环](images/sca.png)

> **SCA 供应链深度治理闭环**：BOM 解析 → 依赖路径构建 → 双源 CVE 匹配 → 杠杆排序 → 三圈版本选型 → 四段哈希链锚定 → verify-rescan 比对 delta → 双签豁免兜底，从发现到治理 7 个环节首尾衔接。

![供应链安全看板](images/供应链安全看板.png)

> **供应链安全看板**：SCA 治理结果一屏总览——依赖组件、许可证、CVE 分布与修复状态按项目聚合展示，支持持续监控的增量对比。

![依赖组件扫描-投毒](images/依赖组件扫描-投毒.png)

> **依赖组件扫描（投毒检测）**：识别供应链投毒风险——标记可疑包、异常版本与恶意特征，三圈版本选型拒绝预发布和 <7 天新发布组件。

![依赖组件扫描-修复路线图](images/依赖组件扫描-修复路线图.png)

> **依赖组件扫描（修复路线图）**：按杠杆排序展示修复路径——先修一个父依赖消除 N 个下游传递漏洞，安全圈 ∩ 兼容圈 ∩ 稳定圈给出最小破坏性升级目标。

**关键设计决策**：

- **杠杆优先而非 CVSS 排序做修复优先级**：CVSS 排序的问题是：一个 HIGH 漏洞可能在 3 个组件中都是传递引入的，修了父依赖就能一次消除全部 3 个。杠杆策略计算的是"修复这个依赖能连带消灭多少个下游漏洞"，把修复从"按严重度排序"变成"按传播面排序"。公式中 λ=3 的权重确保 GPL 等传染性许可证风险不会被大量 LOW 级别 CVE 淹没——许可证合规雷区和安全漏洞在同一个排序框架中竞争优先级。

- **Dependency-Track 作为 SBOM 仓库而非 Dependency-Check 做单次扫描**：Dependency-Check 是文件级 CLI 工具，输出 HTML 报告后没有后续管理能力——这次扫完下次重扫无法对比、无法跨项目聚合、无法配置策略门禁。Dependency-Track 提供 REST API + CycloneDX 原生解析 + 策略引擎，支持持续监控——同一项目的每次扫描结果在 DT 中形成时间序列，新增/修复/残留 CVE 自动 diff。代价是 DT 更重（Java 进程，首次 NVD 同步需 20-40 分钟），但 SCA 治理的核心需求就是持续监控而非一次性扫描。

- **四段哈希链锚定而非仅存扫描 JSON**：修复后如何证明"这次扫描对应的代码和上次是同一个版本"？git_commit→pom_hash→bom_hash→vuln_set_hash 四层链确保每次扫描的 SBOM 和漏洞集都锚定到确定的代码版本。verify-rescan 不是简单重扫，而是比对 delta（eliminated/new/unchanged），check_integrity() 四层逐一校验——任一环节被篡改（如手动修改了扫描报告 JSON）都能检测到。

**闭环**：代码提交 → pre-commit 密钥阻断 → CI 触发 SCA 扫描 → SBOM 上传 DT → CVE 匹配 → 杠杆排序推荐修复版本 → 开发者修复 → verify-rescan 比对 delta → 无法修复的 CRITICAL 走双签豁免（90 天到期自动阻断发布）。

### 2.4 攻击面推演与攻击路径导航

**一句话定义**：将已知漏洞、资产拓扑、网络关系输入自研攻击图引擎，推理可能的攻击路径并量化概率，再有目标地人工验证击破。

**解决的安全本质问题**：云资产生产环境不敢主动扫描（Nessus/OpenVAS 可能触发告警甚至影响业务），但不扫描就无法评估真实攻击面。本质是在"不碰生产"和"了解攻击面"之间找到平衡点。同时传统漏洞列表缺乏攻击上下文——不知道攻击者会从哪个入口打、经过哪些节点、到达哪些核心资产，因此不知道先修哪个漏洞能最大程度阻断攻击链。

**方法论简述**：资产注册 + 指纹引擎 ATT&CK 映射 → 构建有向攻击图（节点=资产，边=攻击动作，权重=(1-exploit_probability)×10+ai_cost_score）→ Dijkstra 加权最短（支持凭据解锁边权重动态降低）→ Yen's K 多条备选路径 → 14 个 ATT&CK 战术顺序校验（禁止跨阶段倒退）→ BFS 四场景概率推演（script_kiddie/advanced/apt 三种攻击者画像 × auth/zone/controls 防御因子）→ 高置信度路径派发人工验证工单 → 确认翻红（exploit_probability=1.0）或驳回阻断（0.01）→ 概率回写触发路径重排。

![攻击链推演引擎](images/攻击链推理引擎.png)

> **攻击链推演引擎**：指纹引擎映射 ATT&CK → 构建有向攻击图 → Dijkstra 加权最短 + Yen's K 备选路径 → BFS 四场景概率推演 → 高置信度路径派发验证工单 → 确认翻红/驳回阻断 → 概率回写触发路径重排。

![资产作战沙盘](images/资产作战沙盘.png)

> **资产作战沙盘**：G6 交互式攻击拓扑——节点为资产、边为攻击动作，高置信度路径聚焦主线，验证工单的派发与裁决在此完成。

![攻击路径验证](images/攻击路径验证.png)

> **攻击路径验证**：单链主线展示当前最危险攻击路径，附 verify_steps 可执行验证步骤，分析师确认翻红或驳回阻断后路径自动重排。

**关键设计决策**：

- **自研图引擎而非 networkx/Neo4j**：networkx 的 Dijkstra 不支持运行时上下文注入——实际渗透中获取凭据后，Edge.get_weight() 需要实时检查凭据池降低 ai_cost_score（匹配的边 exploit_probability×0.9, cost×0.3）。Neo4j 需要独立服务、运维成本和网络依赖。自研 heapq + 邻接表约 150 行，换来了上下文感知的边权重和可控的 Yen's K 临时边移除逻辑。代价是缺少 Betweenness Centrality、PageRank 等高级图算法——但攻击路径场景不需要这些。

- **虚实双轨而非纯推演或纯扫描**：纯推演依赖漏洞库准确性，会漏报未知漏洞；纯扫描对生产有侵入风险。虚实双轨让 LLM 推理攻击路径（虚轨，不触碰生产），同时在关键节点用 nuclei/sqlmap/nmap 的 Docker 沙箱执行实证（实轨，已验证边 is_verified=1）。两条轨在攻击图边权重上融合——推演边低权重（待验证），实证边高权重（已实证），人工验证是最终的权重裁决者。

- **攻击链可视化为单链主线而非全图层序展开**：BFS 层序会把所有可能的攻击路径同时展开——对安全分析师来说是信息过载。单链主线展示当前最优路径（Dijkstra 加权最短），辅以 Yen's K 备选路径列表供切换。分析师沿主线逐段验证，验证结果回写后路径自动重排——下一条最危险的路径浮到主线位置。这是一种"聚焦-验证-重排"的交互模式，而非一次性展示所有可能性。

**闭环**：资产注册 → 指纹映射 ATT&CK → 攻击图构建 → 路径发现 → 概率推演 → 人工验证工单 → 确认/驳回回写 → 路径重排 → 下一条主线推给分析师。

### 2.5 安全基线自动化

**一句话定义**：将模糊的安全要求转化为可验证的检查语句，附测试指导和正例反例，通过 CI/CD 自动执行，让安全检查从人工抽检变为每次提交持续运行。

**解决的安全本质问题**：安全基线的本质问题不是"没有规范"，而是规范不可执行——"应使用安全配置"这类描述开发团队看不懂、测不了，安全团队靠人工抽检覆盖率低、反馈慢。从规范文本到可验证检查之间的鸿沟，是基线落地失败的根本原因。

**方法论简述**：三级可验证体系（红线 20+ 一票否决 / L1 120+ 强制项 / L2 200+ 推荐项）→ 每条语句从"应使用安全配置"改写为"禁止 XXX / 必须启用 XXX / XXX 参数应为 YYY"的可验证句式 → 附 wrong_practice（反面示例）+ right_practice（正面示例）+ detection（编号化可执行测试步骤，带断言和预期结果）→ 映射 CWE 编号和 OWASP Top 10 风险类别 → 溯源 OWASP ASVS / NIST SP 800-53 / CIS / 等保 2.0 标准条款 → 8 类自动化检查脚本（数据库/服务器加固/镜像/容器/Nginx/K8s/Hadoop/数据保护）→ 集成 GitLab CI，MR 触发自动执行，输出 pass/fail + 证据原文，不合规 exit code 1 阻断合并。

![安全基线全景](images/安全基线全景.png)

> **安全基线全景**：三级可验证体系总览——红线（一票否决）/ L1 强制项 / L2 推荐项，按类别展示检查项及 CI/CD 执行结果（pass/fail + 证据原文），不合规项 exit code 1 阻断合并。

![安全基线详情](images/安全基线详情.png)

> **安全基线详情**：单条基线规则详情——"应使用安全配置"改写为可验证句式（禁止/必须/参数应为），附反面示例（❌）/ 正面示例（✅）/ 编号化测试步骤（detection），映射 CWE 与 OWASP 风险类别并溯源 ASVS/NIST/CIS/等保条款。

**关键设计决策**：

- **每条基线附正例反例和测试步骤，不仅写"要求"**：这是基线的教学属性——不是告诉开发者"你应该做 X"，而是展示"这样做是错的（❌反面示例），这样做是对的（✅正面示例），按这个步骤验证（detection 编号化断言）"。补偿措施字段（compensation）给出当技术约束导致无法完全合规时的替代方案（如 WAF 虚拟补丁兜底 ≤30 天）。这套设计让基线从"安全团队的检查清单"变成"开发团队的自检工具"。

**闭环**：基线条目在平台内管理 → CI/CD 触发自动检查 → 不合规标记写入资产图谱节点 → 触发攻击面重算（该节点的 controls 因子降低）→ 修复后重新检查 → 合规状态回写资产图谱。

### 2.6 SDLC 安全门禁

**一句话定义**：把安全从"事后扫描"前移到研发流程的每一步——需求阶段生成安全需求、编码阶段阻断密钥与代码缺陷、测试阶段深度扫描、发布前 12 项门禁聚合裁决，用一张 8 阶段 DAG 把散落的安全能力串成可自动执行的流水线。

**解决的安全本质问题**：安全工具各自为战，开发者不知道在哪个环节该做什么检查，发布决策靠人工拍脑袋。本质是安全能力与研发流程在编排层断裂——工具都在，但没有一个把"需求 → 编码 → 测试 → 发布"串起来的编排器。

**方法论简述**：8 阶段 DAG 并行编排（`ThreadPoolExecutor(max_workers=4)`，拓扑排序波次）→ 需求与威胁建模先行 → 编码阶段密钥阻断 + SAST → 测试阶段 DAST / API / Fuzz / 渗透并行 → release 聚合全部 findings 做 12 项门禁裁决，风险评分 = CRITICAL×40 + HIGH×25 + MEDIUM×10 + LOW×3（0-100）。

**关键设计决策**：

- **拓扑排序波次而非线性流水线**：8 个阶段里，`threat_model` 依赖 `requirements`，`release` 依赖其余 6 个扫描阶段，中间 6 阶段无依赖、可并行。每轮用 `_deps_met` 找出依赖已满足的阶段，`ThreadPoolExecutor(max_workers=4)` 并行执行，比串行快约 3 倍。代价是并发下 Finding 需按 stage 归位再聚合。

- **红线一票否决 + 门禁阈值双保险**：22 条红线（L1 应用 / L2 架构 / L3 基础设施 / L1 AI 应用）标记 `mandatory=True` 不可取消；发布门禁 12 项各有 `critical_max`/`high_max` 阈值，任一 Critical/High 超阈值即 FAIL。两层防线保证"高危问题不可能静默上线"。

- **正则 + LLM + ML 三重引擎而非单一检测**：SAST 用自建正则 14 规则（快）+ Qwen2.5-Coder 语义（准）互补；密钥扫描用 200+ 正则召回 + RandomForest 降噪（`secret_detector.pkl`，压误报）；API 安全四层递进（Schemathesis 属性化 fuzz → Nuclei 已知漏洞 → 自有 Probe 10 项 CWE 映射 → AI 评估）。不同引擎解决不同问题，代价是结果需统一适配层归一。

- **AI 辅助决策而非替代裁决**：DeepSeek 做需求体检（评分 + 差距分析 + 修复建议）和发布决策报告，但门禁裁决本身是确定性的阈值规则（fail→FAIL、warning→CONDITIONAL、pass→PASS），AI 不可达时本地规则回退。保证"AI 给建议，规则做裁决"。

**闭环**：需求生成 → 编码阻断 → 深度扫描 → 门禁裁决 PASS / CONDITIONAL / FAIL → 发布或打回 → 打回项修复后重扫（verify-rescan 比对 delta）。

![SDLC 安全门禁](images/SDLC.png)

> **SDLC 安全门禁**：8 阶段 DAG 并行编排——需求与威胁建模先行，编码阶段密钥阻断 + SAST，测试阶段 DAST/API/Fuzz/渗透并行扫描，release 聚合全部 findings 做 12 项门禁裁决（红线一票否决 + 阈值判定）。

![devsecops流水线](images/devsecops流水线.png)

> **DevSecOps 流水线**：8 阶段 DAG 可视化——需求与威胁建模先行，编码/测试阶段并行扫描，release 聚合全部 findings 做门禁裁决。

![流水线看板](images/流水线看板.png)

> **流水线看板**：各阶段扫描结果总览——按 stage 归位 Finding，风险评分（CRITICAL×40 + HIGH×25 + MEDIUM×10 + LOW×3）实时聚合。

![流水线门禁](images/流水线门禁.png)

> **流水线门禁**：发布前 12 项门禁裁决——红线一票否决 + 各项 critical_max/high_max 阈值，任一超阈值即 FAIL 阻断发布。

![CI-密钥扫描](images/CI-密钥扫描.png)

### 2.7 数据安全治理

**一句话定义**：从数据被识别的那一刻起，沿分类分级→脱敏加密→数据流追踪→跨境合规的完整治理链流转，最终挂载到资产图谱上形成动态数据资产视图。

**解决的安全本质问题**：大多数数据安全工具只做单点检测——PII 扫描只告诉你"这里有身份证号"，分类分级只标"L3 敏感"，脱敏只做字段替换——彼此之间没有数据流连接。安全负责人需要在多个工具之间手工拼接"什么数据、存在哪、谁在访问、合不合规"的全貌。本质是缺少从识别到治理的连贯决策链。

**方法论简述**：数据安全治理链的 7 个环节环环相扣、顺序不可逆——不是简单的流水线，而是下游对上游有硬依赖。

识别（知道数据在哪）是分类的前提——没有识别出字段中的身份证号，就无法确定这个字段属于 L3 个人敏感信息。分类是保护的前提——不知道数据等级就无法决定脱敏策略（L4 必须加密，L1 可以仅令牌化）。脱敏/加密的产物必须反映在数据流图中——敏感字段在脱敏前后是两条不同的数据态，污点追踪时需要区分"原始敏感数据（Source，不可外传）"和"脱敏后的数据（可安全用于测试环境）"。数据流图产出的血缘边是跨境评估的触发器——只有追踪到数据跨越地理边界的边（cross_border 血缘边），跨境评估才有输入——不会遗漏、不会重复。跨境评估结果回写到资产图谱的数据安全标签——同一节点下次扫描时标签已存在，保护策略自动升级，无需重新走全链。

具体实现：(1) 30 类 PII 融合识别（正则 + 银行卡 Luhn 校验 + ckiplab/bert-base-chinese-ner ML NER + DeepSeek 复核）；(2) GB/T 43697-2024 L1-L4 分级，embedding 零样本分类（all-MiniLM-L6-v2）+ 行业策略矩阵（互联网/金融/医疗/政务），分级结果带置信度，低置信度标记漂移待复核；(3) 4 策略角色感知脱敏（admin 见明文 / analyst 部分遮蔽 / viewer 完全替换为 ***）+ FPE(FF1/FF3) + AES-256-GCM 列加密，KEK/DEK 分层密钥管理；(4) AST 污点追踪 25 类 Source × 6 种传播模式 × 20 类 Sink，跨文件调用链 route→service→dao→logger；(5) 数据血缘同步入资产图谱，数据分级标签写入 AssetNode；(6) cross_border 边自动触发 5 法规映射（PIPL 第 38/55/39/66 条 / 数据出境安全评估办法 第 4/5 条 / 数据安全法 第 31/36 条 / GDPR Art.44/46 / CCPA §1798.100），LLM 优先判定 + 规则兜底；(7) DPIA 报告自动生成。

**关键设计决策**：

- **分级分类结果写入资产图谱节点而非独立存储**：传统的做法是数据分类工具维护自己的资产台账，与 CMDB 脱离。SecStack 将数据分级标签（L1-L4）直接写入 AssetNode，这样资产图谱上的同一个数据库节点同时可见：存了什么等级的数据、被哪些服务访问、暴露了什么端口、有没有关联 CVE。数据安全不再是独立维度，而是资产安全画像的一部分。代价是资产模型需要承载数据安全语义——AssetNode 需要 security_level 和 data_classification 字段，这在纯 CMDB 设计中是多余的。

- **跨境合规评估集成在数据流中而非事后单独评估**：数据流图构建时自动识别跨境边（cross_border 血缘边），触发 5 法规映射（PIPL 第 38/55/39/66 条 / 数据出境安全评估办法 第 4/5 条 / 数据安全法 第 31/36 条 / GDPR Art.44/46 / CCPA §1798.100），由 LLM 评估合规状态并生成 DPIA 报告。这比"做完数据流图再手动排查跨境问题"的效率高一个量级，因为跨境评估是数据流分析的自动副产品，而非独立任务。

**闭环**：数据资产识别 → 分类分级 → 保护策略执行（脱敏/加密）→ 数据流追踪 → 跨境自动评估 → 数据分级标签写入资产图谱 → 资产图谱上该节点触发对应等级的保护策略（访问控制/审计强度/备份频率）。

![数据安全治理七环节闭环](images/数据安全治理.png)

> **数据安全治理七环节闭环**：识别（30 类 PII 融合）→ 分类分级（GB/T 43697 L1-L4）→ 脱敏加密（角色感知 + FPE + AES-256-GCM）→ 数据流追踪（AST 污点）→ 跨境自动评估（5 法规映射）→ 分级标签回写资产图谱 → 触发对应等级保护策略。

### 2.8 AI 自主渗透

**一句话定义**：通过 LangGraph 状态机编排 LLM 的渗透决策，按目标指纹精准匹配弹药库武器，在四层安全防线约束下自主执行，最终生成可审计的攻击链路回顾图。

**解决的安全本质问题**：传统渗透测试依赖人的经验和时间——高级渗透工程师稀缺，且人工渗透的覆盖度和一致性无法标准化。但如果让 LLM 直接调用渗透工具，存在三类风险：(1) 越权操作——LLM 可能对未授权目标执行攻击；(2) 参数注入——LLM 生成的命令可能包含 shell 元字符导致命令注入；(3) 输出不可信——LLM 可能将失败的操作报告为成功。本质是在"自动化效率"和"操作安全"之间找到工程上可接受的平衡点。

**方法论简述**：ROE 交战规则确认（授权 IP/端口/路径白名单）→ LangGraph 六节点图调度启动 → brain_think（LLM 推理：分析情报决策下一步动作，含间接 Prompt 注入检测，失败回退规则）→ skill_resolver（按目标指纹 CVE 精确=1.0 / CPE 模糊=0.9 / Tech 栈=0.8 / Keyword=0.7 匹配弹药库五层武器）→ security_guard（白名单校验 + 风险分级：ai_agent=high 需审批 / python_script·yaml_template·go_binary=medium / dictionary·strategy_prompt=low）→ fan_out 并发扇出（Send API，并发度 4）→ tool_executor（按类型分发：dictionary 本地检索 / strategy_prompt 跳过 / 其余调 _run_tool_step 真实 runner，工具未安装自动降级 demo 并标记 degraded）→ aggregator（UDM 实体去重归并）→ router（继续循环 / 情报收集完毕或达迭代上限即终止）→ 渗透结束自动生成 Mermaid 攻击链路回顾图。

![AI 智能渗透图调度与动态编排透视图](images/AI智能渗透图调度与动态编排透视图.png)

> **AI 智能渗透图调度**：LangGraph 图调度全景——ROE 交战规则确认 → brain_think（LLM 决策）→ skill_resolver（按指纹匹配弹药库）→ security_guard（白名单 + 风险分级）→ fan_out 并发扇出 → tool_executor 真实执行 → aggregator 去重归并 → router 循环/终止。

![LangGraph 六节点状态机技术图](images/LangGraph六节点状态机技术图.png)

> **LangGraph 六节点状态机**：PentestState（TypedDict）收敛渗透状态，brain_think → skill_resolver → security_guard → tool_executor → aggregator → router 显式状态图，高危操作标记 requires_approval 走人工审批断点后 resume 恢复。

![AI 渗透靶场演示](images/AI渗透靶场演示.png)

> **AI 渗透靶场演示**：AI 自主渗透在授权靶场上的实战运行——按目标指纹匹配弹药库武器，在 ROE 白名单约束下自动执行探测与利用，攻击链路回放全程可审计。

**关键设计决策**：

- **弹药库五层按指纹匹配而非 LLM 现场生成攻击代码**：GitHub 上成熟的 PoC（nuclei templates / sqlmap / jwt_tool / xray）已经经过实战验证，LLM 的价值在于根据目标指纹（CVE 编号、技术栈、WAF 类型）精准匹配最合适的武器，而非现场写攻击脚本。LLM 生成的代码需要人工审计后才敢执行，但匹配已知武器可以直接走沙箱。后渗透层（frp/冰蝎/哥斯拉）仅做知识注入——AI 生成配置和操作步骤，不自动执行——因为涉及内网穿透和权限维持，自动执行的法律边界和操作风险不可控。这层"知识注入而非自动执行"的隔离设计，是弹药的底线。

- **LangGraph 替代线性 ReAct 的核心收益是显式状态图而非"更聪明"**：V1 线性 ReAct 每轮 Think→Act→Observe 只能跑一个工具，状态散落在循环变量中，难以审计和断点恢复。V3 LangGraph 把状态收敛到 `PentestState`（TypedDict），节点间用 reducer 归并，天然支持人工审批断点——高危操作（ai_agent）标记 `requires_approval`，前端审批后经 `/execute/resume` 恢复。代价是 LangGraph 框架依赖和 Annotated reducer 语义的学习成本。

- **先发现后攻击，针对真实端点而非盲扫根 URL**：Web 目标尚无已发现端点且未跑过 katana 时，攻击面发现守卫强制先派 katana 爬虫爬出真实路径/端点；对 Angular/React/Vue SPA，再正则提取 JS bundle 中写死的 API 路由，补齐 headless 爬虫抓不到的端点。随后 sqlmap/nuclei 针对这些真实端点定向攻击。

- **确定性端点剧本 app_probe，探测不靠 LLM 现场发挥**：敏感文件探测、空字节穿越、布尔 SQLi 三类已知靶场场景用确定性脚本（app_probe）探测，结果稳定可复现；LLM 只负责根据情报决定「何时对哪个端点用哪个剧本」，不现场写探测代码。

**闭环**：ROE 确认 → LangGraph 自主渗透 → 发现漏洞 → 六专家交叉验证（SQLi/XSS/SSRF/CMDi/PathTraversal/IDOR 各独立判定）→ UDM 实体锚定（IP 合法 IPv4/IPv6、CVE 匹配正则、漏洞类型预定义枚举）→ 确认的漏洞写入 FindingStore → probability_updater 回写攻击图边权重 → Mermaid 攻击链路回顾图生成。

### 2.9 AI 安全防御

**一句话定义**：五层 Prompt 注入检测管线 + 输入输出内容护栏 + 按任务类型路由本地/云端模型（代码类→Ollama Qwen2.5-Coder / 文本类→DeepSeek / Prompt 注入→deberta-v3），构成 LLM 调用的前置安全网关。

**解决的安全本质问题**：企业接入 LLM 后面临新的攻击面——用户可通过精心构造的 Prompt 越狱、提取系统提示词、注入恶意指令。传统 WAF 和内容过滤对自然语言攻击无效。本质问题是 LLM 的输入通道缺乏语义级别的安全检查。

**方法论简述**：L0 预处理（NFKC Unicode 规范化 + Base64 解码，防同形字和编码混淆绕过）→ L1 57 条正则规则（6 分类中英双语，~1ms，越狱/提示泄露/数据提取/恶意指令/社交工程/工具滥用）→ L2 HuggingFace deberta-v3 ML 分类器（~50ms，补充规则层对变体语义的盲区）→ L3 DeepSeek LLM-as-Judge 语义分析（零温度，~500ms，成本感知降级：L1×0.15+L2×0.30 < 0.36 时跳过本层）→ L4 10 轮滑动窗口渐进攻击识别（~100ms，检测多轮对话中渐进式越狱）→ L5 PII 脱敏（~5ms，检测输入中嵌入的 PII 并脱敏，每类 PII 叠加 0.15 风险分）。

RiskScorer 加权融合五层分数（L1=0.15 / L2=0.30 / L3=0.25 / L4=0.20 / L5=0.10），阈值 <0.30 放行 / <0.60 告警 / <0.85 阻断 / ≥0.85 人工审核。输出侧三道护栏：PII 重扫防泄露 + 越狱输出检测 + Markdown sanitize 防 XSS。

**关键设计决策**：

- **成本感知降级而非全量走大模型**：五层管线全部走完需要 ~656ms，其中 L3 语义层占 500ms。对于低风险输入（L1+L2 分数极低），跳过昂贵的语义层可以节省 75% 的延迟和 API 成本。这个设计将安全运营成本纳入检测策略——不是所有输入都值得花大模型的钱判断。

**闭环**：用户输入 → 五层管线 → 放行/告警/阻断/人工审核 → 放行的输入进入 LLM → LLM 输出 → 输出护栏（PII 重扫 + 越狱检测 + sanitize）→ 返回给用户 → 全量调用统计写入 deque 200 条缓存。

![AI 安全防御五层管线](images/AI安全防御五层管线.png)

> **AI 安全防御五层管线**：L0 预处理（NFKC + Base64）→ L1 57 条正则（~1ms）→ L2 deberta-v3 ML 分类器（~50ms）→ L3 DeepSeek LLM-as-Judge（~500ms，成本感知降级）→ L4 10 轮滑动窗口渐进攻击识别（~100ms）→ L5 PII 脱敏（~5ms）——RiskScorer 加权融合五层分数，按阈值放行/告警/阻断/人工审核。

![OWASPAI防护体系](images/OWASPAI防护体系.png)

> **OWASP AI 防护体系**：对照 OWASP LLM Top 10 的防护映射——五层 Prompt 注入检测管线 + 输入输出护栏覆盖的威胁类别与对应防护手段。

### 2.10 Agent 工具调用沙箱

**一句话定义**：六步守卫流水线约束 Agent 的工具调用行为，确保 LLM 驱动的自动化操作在受控边界内执行。

**解决的安全本质问题**：Agent 的本质是"让 LLM 决定调用哪个工具、传什么参数"。如果 LLM 被诱导调用危险工具（如执行系统命令、访问文件系统、发起网络请求到内网），Agent 框架本身没有防护能力。本质问题是 LLM 的决策权限和工具的执行权限之间缺乏独立的校验层。

**方法论简述**：每个工具调用必经六步守卫：(1) 权限矩阵校验——工具是否在 Agent 的授权白名单中，操作是否匹配 Agent 的角色（只读/读写/管理）；(2) 频率限额检查——工具调用次数、速率、并发数是否超配额；(3) dry-run 预演——参数组装后先做模拟执行，检查副作用声明是否与实际操作匹配；(4) 破坏性操作确认——delete/drop/rm/truncate 等操作自动生成 P2 工单，要求人工确认；(5) 回滚快照——执行前对受影响资源做快照，失败时自动回滚；(6) 执行 + 审计日志——执行结果和完整上下文写入 AuditTrail。

**关键设计决策**：

- **权限矩阵在校验层而非 Agent 层**：将权限逻辑从 Agent 的业务代码中剥离到独立的 sandbox 模块。Agent 只声明"我需要调用 tool X"，sandbox 决定"你能不能调、调多少、参数合不合法"。代价是每个新工具需要注册权限配置，但换来了权限逻辑的集中可审计——不会出现某个 Agent 偷偷绕过权限检查的情况。

**闭环**：Agent 发起工具调用 → 六步守卫逐项检查 → 通过后执行 → 执行结果 + 审计上下文写入 AuditTrail → HashChainArchive 每 1000 条封存 → Merkle 根锚定。

![AI透明调用链](images/AI透明调用链.png)

> **AI 透明调用链**：Agent 工具调用六步守卫流水线可视化——权限矩阵 → 频率限额 → dry-run 预演 → 破坏性确认 → 回滚快照 → 执行审计，全链路可追溯。

### 2.11 训练与模型安全

**一句话定义**：覆盖模型文件、训练数据、训练流程三个层面的安全检测，确保 AI 模型从训练到部署的完整生命周期安全。

**解决的安全本质问题**：预训练模型和微调数据集通常来自社区——.pkl/.pt 文件可能包含恶意 pickle 字节码（执行任意 Python 代码），训练数据可能被投毒（注入后门触发短语），RLHF 偏好数据可能存在系统性偏差。本质问题是模型供应链的每个环节都可能是攻击入口，而大多数团队只关注推理安全。

**方法论简述**：模型文件层——pickle 字节码反汇编扫描（pickletools 逐指令解析），检测 9 种危险 opcode（REDUCE/GLOBAL/STACK_GLOBAL/INST/BUILD/OBJ/NT/NEWOBJ/EXEC）、8 种可疑模块导入（os/subprocess/socket/requests/pty/builtins/sys/ctypes）、5 种高危函数调用（eval/exec/system/popen/spawn），SHA-256 白名单机制允许审计通过的已知安全模型免检。训练数据层——SFT 数据 4 维扫描（投毒触发短语检测 / PII 泄露检测 / 敏感话题偏差检测 / IsolationForest 分布异常检测）。训练流程层——RLHF 偏好审计（偏好对长度偏差 / 回答风格偏差 / 话题分布偏差检测）+ 训练流审计（T01 数据收集 / T05 模型初始化 / T06 训练执行 / T08 模型发布的检查点审计）。

**关键设计决策**：

- **pickle 字节码级检测而非简单的文件哈希**：文件哈希只能检测"这个文件是不是我之前见过的那一个"——每次模型微调后哈希就变了，无法区分"合法的微调"和"被注入后门的微调"。字节码级检测通过反汇编分析文件的实际操作——如果某个 .pkl 文件在 unpickle 时会执行 os.system()，无论它哈希值是什么都能检测到。代价是检测速度（需要完整反汇编）和误报（某些合法的序列化库确实会用到 REDUCE opcode），通过 SHA-256 白名单机制缓解。

**闭环**：模型文件上传 → pickle 扫描 → 白名单匹配或拦截 → SFT 数据提交 → 4 维扫描 → 通过后进入训练 → RLHF 偏好审计 → 训练流检查点审计 → 模型发布。

### 2.12 渗透测试管理与验证闭环

**一句话定义**：攻击路径推演和 AI 渗透产出的发现，必须经过人工验证工单的确认或驳回，验证结果回写资产图谱并触发路径重排。

**解决的安全本质问题**：LLM 推演和 AI 渗透的输出本质是"假设"而非"结论"——AI 推断某条攻击路径可行，但只有人工验证过的才能作为决策依据。如果不区分"AI 推断的"和"人工实证的"，安全团队将失去对攻击面评估的信任。

**方法论简述**：攻击图高置信度边 → 自动派发 VerificationTask 验证工单（含 verify_steps JSON：具体操作步骤、预期结果、所需工具）→ 安全分析师按步骤验证 → 确认（confirm_verify_task：is_verified=1, exploit_probability=1.0，边翻红）或驳回（reject_verify_task：is_verified=0, exploit_probability=0.0，边证伪）→ _SIM_CACHE.clear() 缓存失效 → Yen's K 自动重排优先级 → 下一条最危险路径浮到主线。

**关键设计决策**：

- **验证工单含可执行步骤而非仅描述漏洞**：传统渗透报告的验证工单写的是"验证 SQL 注入是否存在"，分析师需要自己想办法构造 payload。SecStack 的 VerificationTask 包含 verify_steps JSON——每一步的具体操作命令、预期输出断言、所需工具路径——让验证从"需要渗透经验"变成"按步骤执行并比对预期结果"。这是验证环节的教学属性：把渗透专家的经验编码为可执行验证步骤。

**闭环**：推演/渗透产出发现 → 自动派发验证工单 → 人工按步骤执行 → 确认翻红 / 驳回阻断 → 边权重回写 → 路径重排 → 状态持久化到资产图谱。

### 2.13 合规审计

**一句话定义**：哈希链锚定的防篡改审计日志系统，操作人脱敏保护隐私，Merkle 根锚定支持完整性验证，法规映射引擎将检查结果关联到 PIPL/GDPR/等保条款。

**解决的安全本质问题**：合规审计的痛点不是"没有日志"，而是日志可以被管理员删除或修改——审计方和被审计方是同一角色的情况下，日志缺乏不可抵赖性。同时审计日志中操作人身份直接暴露，存在隐私合规风险。

**方法论简述**：审计事件持续写入 → 每 1000 条打包一个 HashBlock → SHA256(prev_hash + events_json + timestamp) 链式锚定 → Merkle 树根提升验证效率 → operator_hash（SHA256 前 16 位）操作人脱敏 → verify_chain() 自动遍历所有块重新计算 hash 检测篡改 → 法规映射引擎（PIPL/GDPR/CCPA/等保 2.0 / ISO 42001 / GB/T 42888）将检查结果关联到具体标准条款。

```
审计事件流
     │
     ▼
┌─────────┐   ┌─────────┐   ┌─────────┐           ┌─────────┐
│Block 0  │──►│Block 1  │──►│Block 2  │──► ... ──►│Block N  │
│0-999    │   │1000-1999│   │2000-2999│           │   ...   │
└────┬────┘   └────┬────┘   └────┬────┘           └────┬────┘
     └─────────────┴─────────────┴─────────────────────┘
                              ▼
                      ┌───────────────┐
                      │Merkle 根      │
                      │锚定 Git/区块链│
                      └───────────────┘
                              │
                              ▼
            verify_chain() 逐块重算 hash 检测篡改

操作人脱敏：operator "zhangsan" ─► SHA256 前 16 位 ─► operator_hash "a1b2c3d4…"
           （审计时重算比对可验证；无法从日志反向枚举操作人）
```

**关键设计决策**：

- **哈希链而非数据库触发器做审计防篡改**：数据库触发器可以记录变更，但 DBA 可以删除触发器或修改审计表。哈希链的 prev_hash 链式依赖让任何一块的修改都会导致后续所有块的 block_hash 不匹配——篡改必然被检测到。Merkle 根可以定期发布到外部（如 Git commit 或区块链），形成不可篡改的时间锚点。代价是审计日志不能修改——即使是合法的"纠正笔误"也需要追加修正事件而非删除旧事件，存储只增不减。

- **operator_hash 而非明文存储操作人**：操作人身份用 SHA256 前 16 位存储——审计时可以验证"这个操作是不是张三做的"（重新计算张三的 hash 比对），但无法从审计日志反向枚举所有操作人。这是在"可审计"和"隐私保护"之间的工程设计折中。

**闭环**：安全事件触发审计记录 → 缓冲区累积 → 每 1000 条封存 HashBlock → Merkle 根锚定 → verify_chain() 周期性自动校验 → 法规映射引擎生成合规报告。

## 4. 核心亮点

**围绕「以资产图谱为底座、AI 为编排引擎、从发现到修复到验证完整闭环」这条主线**，SecStack 有 6 条区别于传统安全工具的差异化亮点：

**① 一张资产图谱串联一切，是「活的攻防地图」**。所有发现——漏洞、攻击面、数据分级、基线状态、渗透结论——统一写入 FindingStore 并关联到资产节点，查看任意资产时同时可见它的漏洞列表、攻击面标签、数据分级与基线合规状态，这种跨域互见是独立安全工具做不到的。更进一步的机制：影子资产 `unconfirmed`→`confirmed` 转正、孤儿 Finding 自动归因到资产、AI 渗透结果幂等回写台账形成反哺闭环。→ 详见 2.1 · 2.4 · 6.4

**② 以「推演」替代「扫描」，生产环境终于敢被评估**。不在生产环境打真实攻击流量，而是基于资产拓扑做概率推演。自研 Dijkstra + Yen's K + BFS 四场景概率推演（script_kiddie/advanced/apt × auth/zone/controls），虚实双轨并行；推演→派单→人工验证→实证翻红→反哺→优先级重排的完整闭环，每个高置信度路径都带 `verify_steps` 供复现。→ 详见 2.4 · 2.12 · 5.2

**③ LLM 约束在状态机与人工断点中，默认「假设 LLM 不可信」**。AI 只负责策略与调度，不现场写攻击脚本：Web 目标先经 katana 爬取真实路径、SPA JS bundle 提取 API 端点，再针对真实端点攻击而非盲扫根 URL；已知靶场场景走 app_probe 确定性探测（敏感文件/空字节穿越/布尔 SQLi）；其余利用动作经弹药库五层按指纹匹配已知 PoC。V1 ReAct 迭代到 V3 LangGraph 六节点有向图约束行为边界；`brain_think` 内置间接 Prompt 注入检测；ROE 四层防线 + `requires_approval` 人工审批断点 + resume 恢复；哈希链审计日志让每次 AI 决策可追溯、不可篡改。→ 详见 2.8 · 2.9 · 2.10

**④ 每个安全域是端到端方法论，不是脚本堆叠**。既自动跑，又能讲清「为什么这样做、怎样做才对」。供应链端到端治理从 BOM 解析一路走到双签豁免，其中最具杀伤力的是杠杆式修复（修一父依赖消 N 子漏洞）与三圈版本选型（安全∩兼容∩稳定，拒绝预发布与 <7 天防投毒）；数据安全端到端融合 30 类 PII 识别、GB/T 43697 分级与 FPE 脱敏。每个域都是完整方法论而非脚本堆叠，细节见对应章节。→ 详见 2.3 · 2.5 · 2.7 · 2.9

**⑤ 核心引擎全部自研，不是开源拼装**。攻击图引擎用自研 SQLite 闭包表而非 Neo4j，路径发现用自研 Dijkstra / Yen's K / BFS，前端用 AntV G6 自研攻击链可视化；SCA 选 Dependency-Track 而非 Dependency-Check 有明确的治理理由。每一项关键选型都在「关键架构决策」章给了取舍论证。→ 详见 5.1 · 5.2 · 5.3 · 5.4

## 5. 关键架构决策

### 5.1 为什么资产图谱用自研图引擎 + SQLite 闭包表而非 Neo4j

**可选方案**：(A) Neo4j/Cypher 图数据库，(B) networkx 内存图，(C) 自研 heapq + 邻接表 + SQLite 闭包表。

**选择**：方案 C。

**理由**：攻击路径场景需要运行时上下文注入——渗透获取凭据后，Edge.get_weight() 必须实时检查凭据池来降低 ai_cost_score。Neo4j 的图遍历算法不支持这种应用层上下文注入；networkx 的 Dijkstra 权重是静态的，要模拟动态权重只能反复重建图。自研 heapq 版本的 get_weight(context) 可以在运行时读取凭据池和验证状态，动态调整边成本。

**放弃**：Neo4j 的 Cypher 表达力（多跳路径查询、子图匹配）和运维生态（集群、备份、监控）；networkx 的高级图算法（Betweenness Centrality、PageRank、社区发现）。

**权衡**：用约 150 行 heapq + 邻接表代码，换来了上下文感知的边权重和完全可控的 Yen's K 临时边移除。运维上 SQLite 单文件零依赖 vs Neo4j 需要独立 JVM 进程和 2GB+ 内存。代价是图算法能力受限——但攻击路径场景需要的是最短路径和 K 短路径，不需要中心性分析或社区发现。

### 5.2 为什么攻击面评估用推演而非真实扫描

**可选方案**：(A) Nessus/OpenVAS 全网主动扫描，(B) 纯 LLM 推理不验证，(C) 虚实双轨——LLM 推演 + 关键节点实证 + 人工裁决。

**选择**：方案 C。

**理由**：云资产生产环境对主动扫描敏感——Nessus 的插件探测可能触发 WAF 告警、影响业务性能、甚至触发堡垒机的自动隔离策略。但完全不扫描则无法评估真实攻击面——LLM 只能基于已知漏洞推理，未知漏洞（0-day、配置缺陷、逻辑漏洞）会被漏掉。虚实双轨是折中：LLM 基于已知漏洞 + 资产拓扑推演攻击路径（虚轨，零生产影响），在关键节点用 nuclei/sqlmap 的 Docker 沙箱验证（实轨，受控执行），人工最终裁决（确认翻红/驳回阻断）。

**放弃**：主动扫描的覆盖面（能发现未知漏洞但可能影响生产）；纯推演的安全感（不会漏掉"明明一扫就能发现"的问题）。

**权衡**：推演依赖漏洞库的准确性和 LLM 推理的可信度——漏洞库没收录的 CVE、LLM 推理错误的方向都有可能漏报。这个风险通过两条机制缓解：(1) 同时保留 nuclei/DAST 等真实扫描能力作为补充；(2) 推演路径的置信度透明标注（is_verified=0 待验证），不被误读为"已确认的攻击面"。

### 5.3 为什么 SCA 选 Dependency-Track 而非 Dependency-Check

**可选方案**：(A) OWASP Dependency-Check（CLI 工具），(B) Snyk/Mend 商业平台，(C) OWASP Dependency-Track（开源 SBOM 仓库 + 策略引擎）。

**选择**：方案 C。

**理由**：SCA 治理的核心需求是持续监控而非一次性扫描。项目今天扫出 0 个 CVE，不代表下周一 Log4Shell 披露后依然安全——需要同一个 SBOM 持续匹配新披露的漏洞。Dependency-Check 每次运行独立输出 HTML 报告，没有项目维度的历史跟踪和增量对比。Dependency-Track 提供 REST API + CycloneDX 原生解析 + 策略引擎——上传一次 SBOM 后，DT 持续用 NVD/OSV/GitHub Advisory 等源匹配，新漏洞披露后自动通知受影响项目。

**放弃**：Dependency-Check 的轻量（一个 JAR 直接跑，不需要独立服务）；Snyk 的商业漏洞库质量（人工 curated advisories 比 NVD 更准确更及时）。

**权衡**：DT 是 Java 应用，首次启动需 20-40 分钟从 NVD 同步全量漏洞数据库，且内存占用 1-2GB。对于只想"扫一下看看"的场景太重。但 SCA 治理一旦进入持续运营阶段，DT 的 SBOM 仓库 + 策略引擎 + 时间序列 diff 能力是 Dependency-Check 无法替代的。SecStack 在 DT 不可达时自动降级为 OSV.dev 直连查询，保证扫描不中断。

### 5.4 为什么可视化选 AntV G6 而非 D3.js

**可选方案**：(A) D3.js 从零构建交互拓扑，(B) Cytoscape.js，(C) AntV G6 v5。

**选择**：方案 C。

**理由**：攻击图可视化需要一类特定交互——节点拖拽、画布缩放、边高亮、节点展开/收起、路径动画——这些都是图可视化的通用需求。D3.js 是数据绑定库而非图可视化库：用 D3 实现上述交互需要手写力导向布局、手动处理 SVG hit-testing、自行管理节点-边坐标同步——工作量相当于实现了一个简化版 G6。G6 v5 内置了这些图交互原语，自定义节点/边通过继承基类实现，不需要从数据绑定层开始造轮子。

**放弃**：D3.js 的无限定制自由度（可以创建任意非常规可视化形态，不局限于节点-边图）；更广泛的社区生态和示例。

**权衡**：G6 的 API 面比 D3 窄——高度定制化的可视化（如融合时间轴的攻击链动画）需要深入 G6 的自定义元素机制。当前项目中 D3-force 仍用于力导向布局计算（force-worker.js），G6 负责交互渲染——两者各取所长，不是非此即彼。

### 5.5 为什么攻击链可视化用单链主线而非 BFS 全图层序展开

**可选方案**：(A) BFS 层序——同时展示从入口到目标的所有可能攻击路径，(B) 单链主线——展示 Dijkstra 加权最优路径，备选路径按需切换。

**选择**：方案 B。

**理由**：BFS 层序把攻击图一次性全部展开——对安全分析师来说是信息过载。一个中大型资产拓扑可能产生数十条攻击路径，全部渲染在 G6 画布上节点和边密布，分析师无法聚焦。单链主线策略：展示 Dijkstra 加权最短路径（当前最危险的一条），Yen's K 产出的备选路径折叠为侧边栏列表。分析师沿主线逐段验证——确认一条边翻红 → 概率回写触发路径重排 → 下一条最危险路径浮到主线。这是一种"聚焦-验证-重排"的交互模式：不是一次性展示所有可能，而是每次只展示当前最重要的那条。

**放弃**：全图概览的直观性——BFS 层序一眼能看到"攻击面有多大"；一次性对比多条路径的便利——需要切换路径而非并列查看。

**权衡**：单链主线 + 侧边栏备选列表的信息密度低于全图层序。极端情况下，如果最优路径被人工驳回后路径重排结果与之前完全不同，分析师需要重新建立上下文。缓解措施是保留已验证边的翻红/阻断状态在 G6 画布上持久可见，形成"已验证区域"和"待验证路径"的视觉分隔。

```mermaid
    participant HU as 人工验证
    participant VIS as 风险热力图

    SCA->>AG: 写入组件依赖关系 + CVE
    AG->>AG: 风险沿祖先链冒泡
    AG->>ATK: 推送更新后的资产关系 + 漏洞
    ATK->>ATK: 重建有向攻击图 · 路径发现
    ATK->>HU: 高置信度路径派发验证工单
    
    BS->>AG: 写入基线合规状态
    AG->>AG: 不合规节点 controls 因子降低
    AG->>ATK: 触发 invalidate_attack_paths
    
    PEN->>AG: 影子资产(新IP/域名, unconfirmed) + 资产补充(端口/CPE/漏洞)
    PEN->>ATK: probability_updater 回写边概率
    AG->>AG: 影子资产转正 · 孤儿 Finding 归因
    AG->>VIS: 推送资产风险分布
    
    HU->>ATK: confirm/reject_verify_task 确认翻红 / 驳回阻断
    ATK->>ATK: _SIM_CACHE.clear() · Yen's K 重排
    ATK->>AG: 回写边验证状态至资产节点
```

### 6.1 场景一：SCA 漏洞发现 → 绑定资产 → 攻击链推演 → 修复优先级排序

**触发条件**：Java 项目源码上传或 Maven 项目路径指定，触发 SCA 全链路扫描。

**流转路径**：(1) MavenBomGenerator Docker 内执行 cyclonedx 生成 SBOM → MavenDepTreeParser 解析依赖树，过滤 Maven 调解淘汰的幽灵边，构建 introduced_by 传递路径 → OsvClient 批量查询 OSV.dev + 11 个离线 CVE JSON 数据库 → 返回 CVE 列表含严重程度和修复版本；(2) 结果写入 FindingRecord（关联 product_id 和 asset_id）→ 对应组件节点在资产图谱中自动关联漏洞 → AssetSecurityStateORM 更新该节点及其祖先节点的漏洞计数；(3) AttackGraph._load_nodes() 读取更新后的资产关系 + 漏洞数据 → 重新构建有向攻击图 → AttackPathFinder 从入口节点到核心资产计算攻击路径 → 缓存至 AttackPathsCacheORM；(4) 前端作战沙盘 G6 渲染更新后的攻击拓扑 → 包含新发现漏洞的路径自动提升优先级；(5) SCA 修复引擎读取资产图谱中该组件的影响面（被哪些服务依赖、这些服务属于哪些产品线）→ 杠杆排序（传播面×漏洞权重）→ 三圈选型推荐最小破坏性修复版本。

**资产图谱的角色**：将 SCA 的"组件 CVE"转化为"产品线 Y 的服务 X 的依赖 Z 有漏洞，攻击者可能从公网入口经过 X 打到核心数据库"。SCA 告诉你要修什么，资产图谱告诉你要先修什么——因为影响面大的先修。

### 6.2 场景二：安全基线检查 → 不合规标记写入资产 → 触发攻击面重算

**触发条件**：GitLab CI MR 事件触发基线检查流水线。

**流转路径**：(1) pre-commit 钩子先执行密钥检测（200+ 正则 + RF 降噪），命中 sys.exit(1) 阻止提交；(2) MR 合并触发 CI 基线检查 → 8 类检查脚本执行（数据库配置/服务器加固/镜像安全/容器安全/Nginx/K8s/Hadoop/数据保护）→ 逐项输出 pass/fail/warn + 证据原文；(3) 不合规项写入 BaselineRunItem → 关联的资产节点在 AssetAttackSurfaceORM 中更新 controls 因子（如"数据库未启用 TLS"将该节点的 gate_effectiveness 从 0.8 降到 0.3）；(4) 资产 attack_surface 数据变更触发 invalidate_attack_paths → 攻击图缓存失效；(5) 下次攻击路径计算时，BFS 概率推演中该节点的 pass_through gate_effectiveness 降低 → 经过该节点的攻击路径 p_success 上升 → 在 G6 拓扑中该路径边加粗/变色，引起安全团队注意。

**资产图谱的角色**：把"这条基线检查没通过"转化为"这条攻击路径的成功概率上升了 X%"。一条看似不相关的基线配置缺陷（如"Redis 未设密码"），在资产图谱中被自动关联到"攻击者从 Web 入口到核心数据库的路径上多了一个跳板节点"。

### 6.3 场景三：攻击链高置信度推演 → 人工验证工单 → 实证后翻红 → 回写资产图谱

**触发条件**：攻击面推演产出的路径中，某条边的 exploit_probability > 0.7 且 is_verified=0。

**流转路径**：(1) battle_map 自动为该边派发 VerificationTask → 含 verify_steps JSON（具体操作命令、预期输出断言、所需工具路径、预计耗时）；(2) 安全分析师在前端作战沙盘查看工单 → 按 verify_steps 执行验证（可能使用 nuclei 单模板测试或手工 curl 验证）；(3) 验证通过 → 分析师确认 → confirm_verify_task 将该边 is_verified=1, exploit_probability=1.0 → 前端 G6 拓扑中该边翻红（从虚线变实线）；(4) 验证驳回 → reject_verify_task 置 is_verified=0, exploit_probability=0.0 → 该边在后续路径计算中被证伪阻断 → 依赖这条边的路径自动降级；(5) 确认/驳回触发 _SIM_CACHE.clear() 缓存失效 → Yen's K 重新计算 → 下一条最危险的未验证路径浮到主线；(6) 所有验证结果写入 AuditTrail → HashChainArchive 每 1000 条封存 HashBlock → Merkle 根锚定。

**资产图谱的角色**：验证结果不只是"改了一个数据库字段"，而是改变了整个攻击面的评估。一条边翻红可能意味着某个之前被认为是"理论可能"的攻击路径现在被证实为"实际可行"——资产图谱上所有依赖这条边的下游路径同时升级，安全团队的优先级自动重排。

### 6.4 场景四：AI 渗透反哺资产台账 → 影子资产转正 → 孤儿风险归因 → 热力图展示

**触发条件**：AI 渗透（LangGraph 图）会话结束，astream 输出 observations。

**流转路径**：(1) 渗透会话结束，`pentest_asset_writeback.py` 遍历 observations，走两条回写路径——影子资产（新 IP/域名实体 → `asset_nodes` `source='auto_extracted'` `status='unconfirmed'`，挂 unclassified-zone 虚拟根）+ 资产补充（端口/技术栈/CPE/漏洞等客观测量 → fingerprint JSON 幂等并集 + finding_record 签名去重，按 asset_id 关联）；(2) 影子资产进入台账待转正区 → 安全管理员调用 `confirm_shadow_asset` 将 unconfirmed→confirmed，转正后按 名称/域名/IP 模糊匹配自动绑定此前无主的孤儿 Finding；(3) 仍无资产归属的孤儿 Finding → `OrphanCorrelator` 用正则+LLM 提取指纹（IP/域名/端口/技术栈）→ 匹配台账资产 → 命中则 `mark_orphan_resolved` 归因（>20 条走批量 LLM）；(4) 台账最终通过 `heatmap-products` / `heatmap-assets` 以风险热力图形式只读展示资产风险分布与产品线风险面。

**资产图谱的角色**：渗透产出不再是孤立报告，而是实时反哺台账——新发现的影子资产先入待转正区、客观测量数据直接落库、无主发现自动归因。台账从"静态 CMDB"变成"动态闭环"，风险热力图则是这个闭环的只读展示出口。

> 完整机制详见上文「资产图谱引擎 → 能力闭环」小节。

### 7.1 前置条件

- Docker 20.10+ 和 Docker Compose 2.0+

### 7.2 步骤

```bash
# 1. 克隆仓库
git clone <private-repo-url>
cd SecStack

# 2. 配置环境变量
cp .env.example .env
# 编辑 .env，至少填写 DEEPSEEK_API_KEY 和 JWT_SECRET_KEY
```

### 7.3 首次启动注意事项

- Dependency-Track 首次启动需从 NVD 同步全量漏洞数据库（约 20-40 分钟），同步期间 SCA 扫描自动降级为 OSV.dev 直连查询，不影响扫描功能。
- 如果不需要 SCA 持续监控，可以在 `deploy/docker-compose.yml` 中注释掉 `dependency-track` 服务——SCA 扫描仍可通过 OSV.dev + 离线 CVE 数据库正常工作。
- 默认管理员账户密码仅用于本地测试，生产环境请在首次登录后立即修改。

## 8. 技术栈

| 层级 | 选型 | 选型理由 |
|------|------|----------|
| 后端框架 | FastAPI + Uvicorn | 异步原生支持 SSE 流式响应（AI Brain/LangGraph 渗透需要服务端推送），OpenAPI 自动生成为 MCP 工具发现提供 schema |
| 数据库 | SQLite + SQLAlchemy ORM | 单机零运维依赖，闭包表、图邻接表、ORM 模型统一存储；25 个 ORM 模型通过幂等迁移管理 schema 变更 |
| 认证 | JWT HS256 + bcrypt + JTI 黑名单 | 8 小时过期 + 登出立即失效 + RBAC 三级（admin/analyst/viewer），登录失败限速防爆破 |
| 攻击图引擎 | 自研 heapq + 邻接表 | 需要运行时凭据上下文注入（Edge.get_weight(context) 动态调整），现有图库（networkx/Neo4j）不原生支持 |
| 图调度 | LangGraph StateGraph | 替代 V1 线性 ReAct，六节点显式状态图 + 人工审批断点 |
| SCA 引擎 | Docker cyclonedx + Dependency-Track + OSV.dev | 真实运行时依赖解析（非静态 pom.xml 匹配），DT 提供 SBOM 仓库和持续监控，OSV.dev 提供实时 CVE 查询和自动降级 |
| LLM 推理 | DeepSeek API | JSON 模式约束确保 AI Brain 输出可被程序消费（非自由文本），trust_env=False 绕过企业代理直连 |
| 本地 ML | HuggingFace deberta-v3 + bge-small-zh | CPU 推理离线可用，注入检测分类器 + 数据分类嵌入向量，不依赖外部 ML API |
| 前端 | Vanilla JS ES modules + SPA 路由 | 零构建工具链，hash-based 路由实现视图懒加载，安全工具型界面主要工作是 G6/ECharts 自定义渲染，框架复用价值有限 |
| 可视化 | AntV G6 v5 + ECharts + Mermaid | G6 承担交互式攻击拓扑（图专用抽象，内置拖拽/缩放/边高亮），ECharts 承担统计图表（热力图/趋势图），Mermaid 承担流程图/时序图（攻击链回顾） |
| MCP | FastMCP STDIO + SSE 双模 | STDIO 供 Claude Code 本地集成，SSE 供远程工具调用（JWT 认证），安全能力即插即用 |
| 容器化 | Docker Compose 3 服务 | secstack-api + dependency-track + nginx，零 Docker Hub 依赖全本地构建 |
